# 0003-persist-preferences-in-settings-files

`/lingua:off`, `/lingua:on`, `/lingua:model`, `/lingua:effort` の結果は Pi の `settings.json` に書き込み、次のセッションでも有効にする。

## 理由

ユーザーの期待は「一度切ったら切ったまま」である。`/lingua:off` がセッション内の真偽値だけを変えると、新しいセッションも別プロジェクトも既定値の on に戻り、毎回切り直すことになる。拡張を npm からグローバルにインストールする使い方では、これは最初に踏む不具合になる。

設定の解決順序はすでに project > agent > default で、`lib/config.ts` がそれを実装している。書き込みも同じ規則に従わせれば、読みと書きが同じモデルで説明できる。

## 決定

書き込み先は「そのキーを既に設定しているファイル」。どのファイルも設定していないキーだけが agent settings（グローバル）に書かれる。

- キーを設定しているファイル以外へ書くと、その値は上位ファイルに隠され、コマンドが効いていないように見える。所有者を編集するのが唯一必ず効く書き方。
- 所有者が無い場合にグローバルを既定にするのは、グローバルインストールの拡張にとって「全プロジェクトに引き継がれる」が最小の驚きだから。プロジェクト固有にしたい場合は `.pi/settings.json` に `pi-lingua` のキーを書けば、以後そのファイルが所有者になる。
- プロジェクトが未信頼のときは `.pi/settings.json` を読まない・書かない。Pi 本体（`SettingsManager`）がそう振る舞い、未信頼プロジェクトが拡張の挙動を変えられないことが保証される。書けなかった場合はグローバルへ退避し、隠されている事実を通知で明示する。
- 値の削除は「既定に戻す」操作として扱う。`/lingua:effort` の `off` と `/lingua:model` の "Session model" はキーを消す。`"off"` や空文字を値として書くと、下位ファイルの値を打ち消せないまま残る。
- 書き込みは対象ファイルを再読込してからマージする。Pi 本体も同じ read-merge-write を行うため、`pi-lingua` 以外のキーや同時に書かれた設定を壊さない。

## 代替案

- **`pi.sessionState` などセッション付随ストレージに保存する**: セッションを跨げない。要件そのものを満たさない。
- **常に `.pi/settings.json` に書く**: グローバルインストールの拡張が作業ディレクトリごとに設定ファイルを作ることになる。ユーザーが要求していないファイル生成であり、ディレクトリが書き込み不可の場合は切り替えが失敗する。
- **常にグローバルに書く**: キーを既に設定しているプロジェクトファイルに隠され、`/lingua:off` が効かないケースが出る。
- **`/lingua:scope` で書き込み先を選ばせる**: 設定キー・コマンド・状態表示が増える割に、所有者ルールで足りる。プロジェクト固有設定は `.pi/settings.json` に書けばよい。
